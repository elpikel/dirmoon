Dated decision log: what, why, what was rejected.

- 2026-11-24: v1 planned (`.claude/work/dirmoon-v1/`). Owner decisions departing from the handover:
  - Accounts with open sign-up like Ditstar, instead of one user behind a shared password (ADR-0001). A landing page with sign-up was added; it has no reference design.
  - Shared Volumes and SERP Snapshots across Accounts (ADR-0002).
  - Netlify replaces Pagedock for publishing New Idea pages.
  - Existing Site output is a working page: one self-contained `.html` file with CSS inlined, not a content file for the site's layout. Rejected: Markdown, an HTML fragment, a pull request.
  - The Brief gains three Fact Tiles and a Short Answer; the jump strip is built from the sections.
  - Search Console through an in-app Google OAuth flow per Account. Rejected: a service account.
  - Scoring weights 0.4 volume / 0.3 CPC / 0.3 competition weakness, in config.
  - The LLM provider stays undecided behind a seam. Dev uses demo adapters for every external service until credentials exist.
- 2026-11-24: An LLM answer that fails validation (e.g. too few Seeds) is not recorded in the ledger: validation runs inside the `Ledger.fetch/3` function and only validated output is stored, so Oban retries and Resume ask the LLM again. Trade-off: the cost of a rejected answer is not counted in the run's API Cost. Rejected: storing the raw answer and validating after `fetch`, which made every retry and Resume reuse the bad answer and fail without a new call.
- 2026-11-24: Steps 8 (Brief) and 9 (Publish) use a `queued` Step status from the moment the User asks for them until their job starts (and again when interrupted), so a stop/resume before the job starts re-enqueues it instead of stranding the page `writing`/`publishing` with no job. After a final failure of Step 8 or 9, resume does not retry it: the worker has already put the page back (`failed`, or `ready`/`published`), so the Step waits again and the run settles (`awaiting_choice`); the User retries by choosing the Niche or publishing again. This deviates from AC-R11 for the user-triggered Steps. Rejected: resume re-enqueueing a failed Step 8/9, which found no page to work on and skipped.
- 2026-11-24: The runs list "Wyniki" and its status sentence show and count only the newest 50 runs (`Research.list_runs/1`). Accepted for v1 (one owner, few runs); add paging when an Account outgrows it.
- 2026-11-24: "Results are ready" means Step 7 (Scoring) is done, read from the run's Steps (`Research.Run.results_ready?/1`), not from the run's status: a run writing a Brief (`running`) or failed in Step 8/9 still has its results, a run resumed from an earlier Step has none until Step 7 finishes again. The runs list, the run screen's redirect, the results screen and `Niches.choose/2` (plus "not stopped" and idle) all use it. Rejected: a status set (`awaiting_choice`, `done`), which hid the results of a run in Step 8/9.
- 2026-11-24: v1 built (24 tasks, `.claude/work/dirmoon-v1/`). Builder decisions the plan did not dictate, by area:
  - **Accounts and auth.** Magic link only: no passwords, no bcrypt. Settings changes only the email. `Accounts.sign_up/2` answers the same for a new email and one that already has a User (sign-up inserts first and, when the unique index on `users.email` rejects it, signs the existing User in); an invalid email is 422, a failed delivery 503. Mail sender is `{"dirmoon", "contact@example.com"}` (real address undecided). Ecto errors are translated to Polish, default locale `pl`. Accepted: no rate limiting on `POST /sign-up` and `POST /users/log-in`; no production mailer is configured (`Swoosh.Adapters.Local` outside test), so sign-in links are not sent in prod until one is.
  - **Pipeline.** One Step job per run at a time, jobs unique per worker and args. Stop cancels only jobs that have not started; a Step function may return `:stopped` (Step 5 checks between Phrases), which puts the Step back without an error and snoozes the job if the run was resumed meanwhile. Stop, resume, choose and publish all lock the run row first (`Research.lock_run!/1`); choose and publish also need `Research.idle?/1` (`:run_busy`). A Step reads an earlier Step's output only through `Research.step_output/2`; a Step referred to by meaning uses `Steps.number!/1`. A `*_not_configured` reason fails the Step at once, without retries. DB checks: at most five Priority Services, a domain for Existing Site, Step number 1–9, cost ≥ 0.
  - **Ledger.** Per run, keyed by a hash of service, operation and the whole request (so a changed prompt is a new call). Ledger responses carry `fetched_at`, the time the data was bought, so a replay weeks later does not stamp old data as fresh. A city DataForSEO does not know is recorded as "not found" at cost 0 and never asked again. Search Console queries and Netlify deploys are not in the ledger (free; every publish deploys again).
  - **Market data.** Shared Metrics rows are replaced only by a newer `fetched_at`; shared rows are inserted in sorted order so concurrent runs do not deadlock. A Phrase asked for but not returned gets a Metrics row with nil numbers, so it is not asked again for 30 days. Seeds are not stored as Phrases: a Seed the keyword API returns is linked like any other Phrase, and `run_keywords` keeps no origin. Step 4 sends every Phrase of the run (the 400 with the highest Volume, `grouping_phrase_limit`; the rest are rejected as "poza limitem analizy") and owns `run_keywords.status`: a re-run re-decides it and deletes the run's Niches, and their pages with them (`pages.cluster_id` on delete cascade). The LLM sees `run_keywords` ids, never shared ids.
  - **Competition.** SERP Snapshots are append-only, unique per Phrase, location and fetch time; the labels live per run in `serp_assessments` with a `reused_snapshot` flag. Only the 30 highest-Volume kept Phrases in Niches are checked (`serp_phrase_limit`). Verdict: weak when blogs, forums and directories hold more than half (or the SERP is empty), strong when direct competitors hold more than half or at least five places, else medium. An LLM answer that leaves a result unlabelled is rejected; an empty SERP makes no LLM call.
  - **Current Positions.** Every matched position is stored, for kept and rejected Phrases, rounded to one decimal, best position when a query repeats; Quick Wins are 8–20 inclusive on the rounded value (`Phrases.quick_win_range/0`). Window: the last 90 days to yesterday (UTC), up to 5000 queries, property `sc-domain:<domain>`. No Connection, an expired one or no access to the domain skips the Step with a reason instead of failing the run. The refresh token is encrypted with `Plug.Crypto` keyed by `secret_key_base`: changing that secret means every Account reconnects. The Google email is read from the `id_token` without verifying its signature (it comes straight from the token endpoint and is display only). Disconnect does not revoke at Google. `filter_parameters` hides `code`, which also hides other params with "code" in the name.
  - **Scoring.** Volume and CPC are `log1p`-normalised against the run's highest value; weakness is the weak share of the Niche's pooled labels, 0.5 when none of its Phrases was checked. The Niche's CPC is Volume-weighted over the Phrases that have one. Score is 0–10 to one decimal; a Niche is worth going after from 4 (`Niches.Scoring.worth_threshold/0`, the one home of that rule). Weights must sum to 1 ± 0.01.
  - **Page and scrubber.** A Placeholder is exactly `[` upper-case letters, spaces, hyphens `]`; other bracketed text is ordinary text. The LLM never sets phone, e-mail, address, business name, nav links, closing prompt or Plausible domain; every other free-text field it writes is scrubbed of prices, phones, e-mails and addresses. The User's own edits are never scrubbed. Only the H1 and one section question are required; a blank field renders as a Placeholder. Both Modes render the same template. Known misses, accepted: prices in words, "zł 80", "1.5 zł", addresses without `ul./al./pl./os.` (incl. "ulica …"), obfuscated e-mails, phones written `600.100.200`, amounts of 10+ ungrouped digits; and any bare 9-digit number (REGON, order number) becomes `[TELEFON]`. Plausible uses the legacy `script.js` tag with `data-domain`, rendered only for a valid host.
  - **Publishing.** Both Modes can publish and download (the plan had publish for New Idea, download for Existing Site). The hosting seam is `create_site/1` + `deploy/1`: one Netlify site per page, its id stored before the deploy so a retry never creates a second site; publishing again deploys to the same site. Netlify is polled inside the job (3 s × 100). A failed publish puts the page back to `ready`/`published` with the error. One Brief is written per run at a time (partial unique index); a Niche that already has a page returns that page instead of writing another. The download is an attachment `<slug>.html`.
  - **Screens.** `/app` redirects to the new research screen. The run screen redirects to the results only on the live change to Awaiting Choice; opening such a run shows a "Zobacz wyniki" button. The runs and pages lists are not live. Accepted caps: pages list newest 50, the Phrases and rejected views 500 rows, the run screen's checked-Phrases feed 8 and not reloaded on mount. CPC is shown in USD as DataForSEO returns it, not converted to PLN. The New Idea Niche tile shows the most direct competitors in one checked Phrase's top 10. CSV export: UTF-8 with BOM, CRLF, dot decimals, formula cells prefixed with `'`. The API Cost estimate uses unverified per-request prices (`cost_estimates`: 0.09 / 0.09 / 0.002 USD, LLM 0).
- 2026-11-24: No external client has been run against its live service; each was written from the documentation and tested against `Req.Test` stubs. No LLM provider adapter exists at all (only `Demo` and `NotConfigured`). Assumptions to check on the first real run:
  - DataForSEO: `result` is null on a failed task; the body of a 401; `/locations/pl` in lower case; a city has `location_type == "City"` and is matched on the city part of `location_name`; how search volume answers for unknown keywords; the text of error 40501; `40102 "No Search Results."` means an empty SERP; cost is the top-level `cost`.
  - Google: `prompt=consent` re-issues a refresh token; 403 means no access to the property; a missing `rows` means no data; `sc-domain:` is sent as `sc-domain%3A`; host `searchconsole.googleapis.com`.
  - Netlify: 422 on a site-name conflict; 2xx on deploy; the `rejected` deploy state; `index.html` at the zip root; `ssl_url`; 401 for a bad token.
- 2026-11-24: The glossary renames changed stored JSON keys (`brief.fact_tiles`, the `"trend"` key of ledger rows) and a ledger operation string (`"phrase_ideas"`) without a data migration, because no database held pre-rename data: nothing had been deployed, and the only database with data, `dirmoon_dev`, was created after the renames. From the first deploy on, a rename of a stored key, status or operation string needs a data migration in the same change.
- 2026-11-24: No `Decimal` reaches a jsonb column. Jason encodes a `Decimal` only when it happens to be compiled after Decimal, so Step 2 stored a Decimal CPC in the test build and crashed in the dev build. Values bound for jsonb go through `Dirmoon.JsonSafe.encode/1` at the boundaries (Metrics `raw` and Trend, every ledger request and response, every Step output); the Repo's Postgrex JSON library, `Dirmoon.Repo.StrictJson`, raises on a `Decimal` in any jsonb value, so every build behaves the same and a missed conversion fails the tests. Calendar structs are still allowed there (Jason always encodes them; Oban stores `DateTime`s in job errors). Rejected: relying on Jason's optional Decimal support.
- 2026-11-24: Demo Data text is marked with a lower-case `(demo)` prefix (`Dirmoon.demo_marker/0`). The earlier `[DEMO]` matched the Placeholder pattern and rendered as placeholder pills on the page preview.
- 2026-11-24: Signed-in Users never see the landing page (owner): `GET /` and `POST /sign-up` redirect them to `/app` (`UserAuth.redirect_if_user_is_authenticated/2`), and nothing in the app nav links to `/`. The sign-in page stays open to a signed-in User, because Settings sends them there to re-authenticate (sudo mode).

The light dotted page, nav card, eyebrows and headlines are for the landing page and sign-in only; there is no marketing content in the app. The reference's screen 1 pitch (hero, "jak to działa") lives only on the landing page; the new research screen is a tool view with the form and the Account's five latest runs, and its status sentence comes from the chosen Mode and the Search Console Connection (`Research.NewRunStatusLine`). Big headlines went away: the results' counts sentence is the small heading above the Niche list; the run and page headlines repeated their status sentences and were deleted. Settings uses the app shell too.
